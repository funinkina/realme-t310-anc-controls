# Android reserves native earbud ANC for privileged apps

Android does have first-party plumbing that puts earbud noise control into the OS: a slice on the Bluetooth device-details page, a structured device-settings provider added in Android 16 with a dedicated `DEVICE_SETTING_ID_ANC` toggle, and a "Noise Control" button in the volume panel. **Every one of these surfaces is found through Bluetooth device metadata that only a `BLUETOOTH_PRIVILEGED` (signature|privileged) component can write.** On a Pixel that writer is Google Play services Fast Pair, and in practice the controls have shipped only for Pixel Buds Pro and Pro 2. Samsung (One UI) and Apple (iOS) follow the same pattern: buds from the phone maker become "first-class" because the OS image ships a trusted, preinstalled app or OS code that speaks the buds' proprietary protocol, not because of a public API. OPPO and OnePlus phones do the same with a system "Wireless Earphones" app, but GSMArena reports that realme phones still send realme buds to the realme Link app. The user's own Pixel on Android 17 confirms the gap: Fast Pair writes only the T310's left, right and case battery levels, with no settings slice and no provider pointer. **So yes, a realme Buds T310 owner on a stock Pixel needs an app. The most native option they can get is the one they have already built: a Quick Settings `TileService` that talks RFCOMM.** It can be improved with `CompanionDeviceManager` presence callbacks and the in-app "add tile" prompt, but no public route reaches Settings or the volume panel.

## Pixel Buds feel native because Google's privileged code wires them in

On a Pixel, Google describes Pixel Buds settings as the Pixel Buds app **"directly integrated to your system settings"**. The page is reached from Settings > Connected devices > gear icon, and noise-control modes (ANC, Adaptive, Transparency, Off) appear there only while the buds are connected. On any other Android phone, the same controls need the Pixel Buds app from Google Play ([Pixel Buds Help](https://support.google.com/googlepixelbuds/answer/7685360?hl=en)). The volume panel route has a rocky history. Android 15 Beta 4 dropped the ANC buttons from the redesigned volume panel; even while they were visible in beta, they "didn't work with other devices" besides Pixel Buds Pro/Pro 2 ([Android Authority](https://www.androidauthority.com/android-15-anc-controls-3474984/)). **Noise Control returned on 2024-09-29 as a server-side rollout**, sitting next to Spatial Audio and Live Caption in the volume panel's overflow, again for Pixel Buds Pro and Pro 2 only ([9to5Google](https://9to5google.com/2024/09/29/pixel-buds-noise-control/)). It broke again after the March 2026 update, and affected users tried clearing the Pixel Buds app's data to fix it ([Android Authority](https://www.androidauthority.com/pixel-buds-anc-controls-disappear-3662799/)). The feature changes between monthly builds and responds to clearing a Google app's data. That is the signature of a feature delivered by Google's own apps and server flags, with AOSP providing only the host UI.

The AOSP side shows exactly where that host UI gets its content. Settings' device-details page reads `METADATA_ENHANCED_SETTINGS_UI_URI` (key 16), described as the "URI to the enhanced settings UI slice", and renders it with `SliceLiveData` ([BluetoothFeatureProviderImpl.kt](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/main/src/com/android/settings/bluetooth/BluetoothFeatureProviderImpl.kt); [BluetoothDeviceDetailsFragment.java](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/main/src/com/android/settings/bluetooth/BluetoothDeviceDetailsFragment.java)). A second "extra control" slice comes from the `HEARABLE_CONTROL_SLICE_WITH_WIDTH` tag inside `METADATA_FAST_PAIR_CUSTOMIZED_FIELDS` (key 25) ([BluetoothUtils.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SettingsLib/src/com/android/settingslib/bluetooth/BluetoothUtils.java)). The SystemUI volume-panel ANC component reads that same key-25 tag and shows itself only when the slice loads ([AncSliceRepository.kt](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/src/com/android/systemui/volume/panel/component/anc/data/repository/AncSliceRepository.kt); [AncAvailabilityCriteria.kt](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SystemUI/src/com/android/systemui/volume/panel/component/anc/domain/AncAvailabilityCriteria.kt)).

Android 16 added a richer path. The `settingslib/bluetooth/devicesettings` package is an AIDL provider framework with typed preferences, including multi-toggles, and a reserved **`DEVICE_SETTING_ID_ANC = 1001`** ([DeviceSettingId.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SettingsLib/src/com/android/settingslib/bluetooth/devicesettings/DeviceSettingId.java)). The directory exists on `android16-release` and is absent on `android15-release` ([android16](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/packages/SettingsLib/src/com/android/settingslib/bluetooth/devicesettings/); [android15](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/packages/SettingsLib/src/com/android/settingslib/bluetooth/devicesettings/)). Settings finds the provider app only by reading `DEVICE_SETTINGS_CONFIG_PACKAGE_NAME`, `_CLASS` and `_ACTION` out of key 25. It then binds the named service with **no package allowlist or signature check** ([DeviceSettingServiceConnection.kt](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/SettingsLib/src/com/android/settingslib/bluetooth/devicesettings/data/repository/DeviceSettingServiceConnection.kt)). These interfaces live in SettingsLib, not the public SDK.

## One permission gate closes every native surface

The whole design is "privileged writer, public reader". Settings and SystemUI will render a slice or bind a provider from any package, but only if Bluetooth metadata names it. `BluetoothDevice.setMetadata()` is `@SystemApi` and requires `BLUETOOTH_CONNECT` plus **`BLUETOOTH_PRIVILEGED`, whose protection level is `signature|privileged`** ([BluetoothDevice.java](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/BluetoothDevice.java); [AndroidManifest.xml](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/res/AndroidManifest.xml)). A Play Store app cannot hold that permission on a stock Pixel. The obvious public alternative also leads nowhere. Settings has a controller that would list `CompanionDeviceManager`-associated apps on the device page, but its `isAvailable()` is hard-coded to `return false` ("Do not show this preference for now") ([BluetoothDetailsCompanionAppsController.java](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/main/src/com/android/settings/bluetooth/BluetoothDetailsCompanionAppsController.java)). The Bluetooth standards offer no way around this either. LE Audio defines volume, microphone and hearing-aid preset control, but **no Bluetooth SIG profile for ANC or transparency** was found, so earbud ANC is always vendor-proprietary ([Bluetooth SIG LE Audio specs](https://www.bluetooth.com/learn-about-bluetooth/feature-enhancements/le-audio/le-audio-specifications/)).

| Surface | How the OS finds the controls | Who can enable it | Public API? |
|---|---|---|---|
| Settings device-details slice | `METADATA_ENHANCED_SETTINGS_UI_URI` (key 16) | `BLUETOOTH_PRIVILEGED` writer (GMS Fast Pair) | No |
| Settings extra-control slice | key 25 `HEARABLE_CONTROL_SLICE_WITH_WIDTH` | Same | No |
| Android 16+ device-settings provider (`DEVICE_SETTING_ID_ANC`) | key 25 `DEVICE_SETTINGS_CONFIG_*` | Same | No (SettingsLib AIDL) |
| Volume panel "Noise Control" | key 25 slice tag | Same; shipped for Pixel Buds Pro/Pro 2 only | No |
| Companion app on device page | CDM association | Anyone, but the controller is disabled | Yes, but not displayed |
| Quick Settings tile | `TileService` | Any app | Yes |

Google's only sanctioned route for third-party buds goes through Fast Pair. The Fast Pair **Hearable Controls extension (message group 0x08)** defines Get/Set/Notify ANC state with Transparent, Adaptive, Off and ANC mode bits. Its spec says "on the Seeker side, Fast Pair will have the UI and logic to set, get and save the state" ([Fast Pair Hearable Controls](https://developers.google.com/nearby/fast-pair/specifications/extensions/hearablecontrols?hl=en)). ANC support is optional for certification ([Fast Pair certification guidelines](https://developers.google.com/nearby/fast-pair/fast-pair-certification-guideline)). This must be built into the earbud firmware, so an app developer cannot add it. No source confirms that Pixel actually renders this UI for any non-Google earbud, and coverage of the volume-panel feature says it works only with Google's own buds ([PhoneArena](https://www.phonearena.com/news/android-15-might-return-anc-controls-to-the-volume-panel_id161781)).

## Samsung, OPPO and Apple bake it into the OS image too

Samsung moved Galaxy Buds controls out of a standalone app and into One UI in two steps. In One UI 7, long-pressing the Quick Panel volume slider exposes noise-control mode, EQ and related settings for Galaxy Buds3 and Buds3 Pro ([Samsung Newsroom](https://news.samsung.com/ca/galaxy-buds3-series-offers-enhanced-convenience-on-the-galaxy-s25-series)). Then **a June 2025 Galaxy Wearable update moved ANC, touch controls, EQ and firmware updates to Settings > Bluetooth** ([9to5Google](https://9to5google.com/2025/06/23/samsungs-galaxy-buds-controls-are-relocating-in-one-ui/)), and Samsung formalised this in One UI 8 ([Samsung Community](https://us.community.samsung.com/t5/Discussions/Galaxy-Buds-3-Pro-OneUI8-A-Step-Backward-in-Ecosystem-Design/m-p/3356296)). Every source describes this for Galaxy Buds on Galaxy phones only.

OPPO uses the same approach. On ColorOS 11+, users go to "Bluetooth > OPPO Enco Free2 > Earbud Functions", while users of other phones are pointed to HeyMelody ([OPPO Enco Free2](https://www.oppo.com/en/accessories/enco-free2/)). OPPO also says that on ColorOS or OnePlus phones the "Wireless Earphones" app must be installed or updated through the App Market before that Bluetooth-settings entry works ([OPPO Enco Air3 Pro](https://www.oppo.com/uk/accessories/enco-air3-pro/)). In other words, the built-in experience is a system app hosted inside Settings. realme is the odd one out within its own corporate family. **GSMArena's Buds T200 review notes "you still have to use the Realme Link app on a Realme phone"**, while on OnePlus and OPPO phones the features "just appear within Bluetooth settings" ([GSMArena](https://www.gsmarena.com/realme_buds_t200_review-news-68981.php)). That review dates from 2023, and no newer source shows realme UI adding a built-in path for T-series buds.

Apple is the fully vertical version of the same idea. AirPods listening modes live in Control Center (hold the volume slider) and in Settings under the AirPods' name near the top, and no app is involved ([Apple AirPods User Guide](https://support.apple.com/en-us/guide/airpods/dev6d977ff21/web)). The EU's DMA interoperability push has so far opened proximity pairing and notification forwarding to third-party accessories in iOS 26.3, EU only, and not noise-control UI ([Cult of Mac](https://www.cultofmac.com/?p=901218)). Across all four ecosystems, "first-class" means the phone maker ships trusted code that already speaks its own buds' protocol. That makes it a business arrangement as much as an API.

## The T310 on this Pixel gets battery levels and nothing more

The realme Buds T310 lists Google Fast Pair and the realme Link app among its features ([Vijay Sales](https://www.vijaysales.com/p/231137/realme-buds-t310-tws-earbuds-with-12-4mm-dynamic-bass-driver-upto-40-hours-playback-46db-hybrid-noise-cancellation-agile-white)), and iXBT calls it the first in its line with Fast Pair ([iXBT](https://www.ixbt.com/ds/realme-buds-t310-review.html)). realme's marketing mentions Fast Pair only for pairing, and no source says the T310 firmware implements Hearable Controls. On-device evidence settles the question for this unit. On the user's Pixel (Android 17, CP3A.261005.005), `dumpsys bluetooth_manager` logs "Custom metadata changed" for **keys 10, 11 and 12 only, which are the untethered left, right and case battery keys**. It shows no key 16 settings-slice URI and no key 25 customized fields. No realme, OPPO, HeyMelody or Pixel Buds package is installed. Fast Pair is active for the T310 and supplies battery levels, but nothing on the phone advertises an ANC slice or provider. That observation comes from the coordinator's local `adb` session and has no external URL. Opening the T310's Bluetooth device-details page and seeing no noise-control section would confirm it from the UI.

The official alternative is weaker than what the user already has. realme Link is realme's catch-all accessory app. Its ANC control is an in-app toggle, and it requires a realme account and region selection before the buds can be used with it ([GSMArena](https://www.gsmarena.com/realme_buds_t200_review-news-68981.php)). realme says the buds work over plain Bluetooth and that the app is needed only for customisation and firmware updates ([realme support](https://realme.com/in/support/kw/doc/2070268)). The only app-free shortcut is a 2-second press-and-hold on either earbud, which switches between noise reduction and transparency ([realme support](https://www.realme.com/ph/support/kw/doc/2043682)). No source documents a realme Link Quick Settings tile, widget or persistent notification. The underlying RFCOMM protocol is shared across OPPO, OnePlus and realme, and community tools such as the Noctalia `oppo-pods` plugin control ANC on 200+ models over it ([oppo-pods](https://github.com/noctalia-dev/community-plugins/tree/main/oppo-pods)). The user's app already speaks this protocol (frame `AA 0A 00 00 04 04 01 03 00 01 01 <mode>`, ACK 0x84) with only `BLUETOOTH_CONNECT`.

### Making the existing tile as native as a public app can get

Three public APIs close most of the remaining gap. `StatusBarManager.requestAddTileService` (API 33) lets the app show the system's own "add this tile" prompt, so the user does not have to find it in the QS editor ([StatusBarManager](https://developer.android.com/reference/android/app/StatusBarManager)). A `CompanionDeviceManager` association with `startObservingDevicePresence` and a `CompanionDeviceService` (API 31) wakes the app when the T310 connects. The app can then open RFCOMM, read the current mode and refresh the tile state before the user looks at it. CDM-associated apps also get relaxed background and foreground-service start limits ([CompanionDeviceManager](https://developer.android.com/reference/android/companion/CompanionDeviceManager); [Companion device pairing](https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing)). An ongoing notification while the buds are connected is an optional third surface. None of these places the control in Settings or the volume panel. The CDM association will not even appear on the device page, because that controller is disabled.

## Conclusion

Android is not missing a native ANC home. It has three, and the Android 16 provider framework even reserves an ANC slot. What it lacks is a public key to them, because each surface is reached through metadata that only Google's Fast Pair stack can write. For a T310 owner, there are only two ways into those surfaces, and neither is open to them. realme could ship Fast Pair Hearable Controls in firmware and hope Pixel renders it for third-party buds, which is unconfirmed. Or a rooted or custom-ROM device could write key 25 itself from a privileged context, which is plausible but untested and outside stock Pixel.

The practical answer is that the user's Quick Settings tile is the most native ANC control a realme T310 can have on a stock Pixel running Android 17. It is closer to native than realme's own app, which offers no tile and requires an account. Adding CDM presence so the tile is live and correct when the buds connect, and `requestAddTileService` for one-tap setup, is the last step a public app can take. Further progress depends on realme and Google, not on more app code.

## Correction (2026-10-27, after delivery)

A complete metadata dump (`adb shell dumpsys bluetooth_manager`) shows the section "The T310 on this Pixel gets battery levels and nothing more" is wrong on one point. **Key 25 is set for the T310**: `DEVICE_SETTINGS_CONFIG_PACKAGE_NAME=com.google.android.gms`, `DEVICE_SETTINGS_CONFIG_CLASS=com.google.android.gms.chimera.GmsBoundBrokerService`, `DEVICE_SETTINGS_CONFIG_ACTION=com.google.android.gms.fastpair.ACTION_BIND_DEVICE_SETTINGS_CONFIG_PROVIDER`. So Google Play services' Fast Pair is registered as the Android 16+ device-settings provider for these buds. The buds also advertise the Fast Pair Message Stream RFCOMM service (UUID `df21fe2c-2515-4fdb-8886-f12c4d67927c`). Hearable Controls ANC messages travel over that channel. Whether the provider shows a noise-control toggle still depends on the T310 firmware answering Hearable Controls (message group 0x08), and that remains untested. The earlier conclusion stands until that test is run: no ANC control in Settings has been observed for the T310.

## Test result: the T310 does not implement Fast Pair Hearable Controls (2026-10-27)

A throwaway build on the user's Pixel opened the Fast Pair Message Stream (RFCOMM, UUID `df21fe2c-…`, channel 5) by retrying inside the ~5 s gap Google Play services leaves before it reconnects. It then sent "Get ANC state" (`08 11 00 00`) three times on a confirmed-open channel. Each time the buds sent only Device Information frames: Model ID `0x203170` (`03 01 0003 203170`), each bud's BLE address (`03 02 …`), and battery (`03 03 0003 5a5a7f` = 90 % / 90 % / case unknown). The ~1–4 s windows before Play services reclaimed the channel never brought a Notify ANC state (`08 13`), an ACK, or a NAK. Play services' own logs show only its device-info handling for these buds, with no ANC activity. **Conclusion: the T310 firmware does not support Fast Pair ANC control, so the Settings/volume-panel route is closed without a realme firmware change.** The proprietary RFCOMM channel-1 protocol the user's app uses remains the only way to switch ANC from the phone.
